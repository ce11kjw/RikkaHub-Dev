# 调试

**先想清楚再动手改。** 猜着改代码，会同时引入新问题和掩盖真问题。

## 第一步：把现象说准确

动手之前先写清楚：

- **实际发生了什么**（报错原文、错误码、具体数值）
- **期望发生什么**
- **怎么重现**（什么操作、什么输入、是否必现）
- **什么时候开始的**（改了什么之后、升级了什么之后）

说不清这四条就开始猜，就是在浪费时间。

## 第二步：提假设，不要提结论

列出 2-4 个**可能**的原因，按可能性排序。每个假设都要能回答："如果是这个原因，应该能观察到什么？"

举例：服务返回 502。
- 假设 A：上游挂了 → 应该能 ping 通上游但端口不通
- 假设 B：端口没监听 → 本机 curl 127.0.0.1 也该失败
- 假设 C：防火墙拦了 → 本机通、外部不通

**这三个假设的验证方法完全不同**，这就是为什么要先列出来。

## 第三步：一次只验一个，找能一票否决的证据

优先做**成本低、能排除最多可能**的验证。

判断链路要**分段测**，不要一步跳到结论：

```
本机回环 → 本机到网关 → 本机到目标 → 目标本身
```

哪一段断了，问题就在哪一段。

## 第四步：拿到证据再改

如果验证结果不支持任何假设，说明假设集合错了，**回去重新列**，而不是随便改点东西看看。

改完必须**能解释**：为什么这个改动会让现象消失。说不出来，就只是碰巧掩盖了。

## 常见陷阱

- **把自己当变量**：`pkill -f xxx` 会杀掉自己的命令行；`grep xxx` 会匹配到自己。用 bracket 或变量拼接避开。
- **把"没观察到"当"不存在"**：日志没打出来，可能是日志级别、可能是没走到那条路径、也可能是输出被缓冲了。
- **一次改多个地方**：改完好了，但不知道是哪个改动起的作用，也没法保证其它改动没引入新问题。
- **相信症状相似的旧经验**：上次是 A 导致的，这次看起来像 A，但可能不是。先验证再说。

## 报结论的方式

1. **根因是什么**（一句话）
2. **证据是什么**（具体日志行、命令输出、对比实验）
3. **怎么修的**，为什么这样能修好
4. **为什么之前没发现**（如果有价值）

不确定的部分直接说不确定，不要编一个听起来合理的解释。

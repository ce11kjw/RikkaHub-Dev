# 技术写作

**写给要照着做的人看。** 判断标准只有一个：读者能不能据此把事情做成。

## 先想清楚三件事

1. **谁读**：同行？新手？未来的自己？决定用不用术语、要解释到多细。
2. **读完要做什么**：是照着操作，还是理解原理，还是查参数？决定结构和详略。
3. **读不到什么**：读者手上没有你的上下文、没看过这次对话、不知道你为什么这么做。

## 结构：先结论，再理由，最后细节

```
这是什么 / 结论是什么
  ↓
为什么（必要条件、取舍）
  ↓
怎么做（步骤、命令、参数）
  ↓
边界与坑
```

读者随时可能只读第一段就关掉，所以最重要的必须在最前面。

## 具体，不要形容

| 差 | 好 |
|---|---|
| 性能明显提升 | 从 1.2s 降到 180ms |
| 支持多种格式 | 支持 png / jpg / webp |
| 配置一下就能用 | 改 `config.yaml` 的 `port: 8080` |
| 可能出现问题 | 磁盘写满时返回 500（实测） |

**数字、路径、命令、报错原文** 比任何形容词都有用。

## 步骤要能照着敲

- 代码块里放**真的能跑**的命令，不要 `your_path_here`
- 有前提条件先说（需要什么权限、装什么、先改哪个文件）
- 每步之后说**应该看到什么**，读者才知道自己做对了没有
- 报错怎么办写一句

## 删掉这些

- "值得注意的是"、"需要强调的是"、"众所周知"
- "简单来说"、"Basically"、"In order to"（直接说 "to"）
- 三个形容词堆在一起（"高效、稳定、可靠的方案"）
- 重复上文的总结段
- 为了凑字数展开的废话

## README 的最小结构

```markdown
# 名字
一句话说清是什么。

## 为什么用它
解决什么痛点。不吹。

## 快速开始
三条命令以内能跑起来。

## 用法
常见场景，每个配一个例子。

## 配置
有哪些项，默认值是什么。

## 已知限制
诚实列出做不到的事。
```

## 提交说明

```
类型(范围): 做了什么（一句话，祈使句）

为什么这么做。不这么做会怎样。
如果修的是 bug，说清根因。

影响范围 / 需要注意的点
```

类型：`feat` 新功能 / `fix` 修 bug / `refactor` 重构 / `docs` 文档 / `perf` 性能 / `test` 测试。

**不要把修改的文件列表复制进提交说明** —— git 自己会列。

## 写完自己读一遍

- 把上下文忘掉从第一行读，能不能看懂？
- 每句话是否必要？删掉会不会影响理解？
- 有没有哪句是"看起来对但没信息量"的？

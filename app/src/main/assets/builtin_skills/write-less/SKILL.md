# 少写

写代码最容易犯的错不是写错，是**做多了**。多做的东西要维护、要理解、要跟着改，比一开始少做贵得多。

## 动手前先问三个问题

1. **这件事真的需要做吗？** 用户要 X，真正的痛点可能是 Y，而 Y 已经解决了。
2. **平台/标准库已经有吗？** 语言内置函数、系统 API、现有依赖里的工具 —— 先去查，别凭印象觉得"大概没有"。
3. **现有的哪段代码最接近？** 改一个函数，比新建一个模块省事得多。

三个都过不了，才开始写。

## 最小必要改动

- 只改需要改的函数，不顺手重构旁边的代码
- 不为"以后可能需要"预留抽象（没有第二个调用方之前，抽象都是负担）
- 不新增配置项，除非用户明确要求可配置
- 不引入新依赖来解决标准库能解决的问题

**判断标准**：这个改动里，有没有哪部分删掉之后需求依然满足？有，就删掉。

## 先暴露假设

动手前把不确定的地方说清楚：

```
我按这些假设实现：
1. 输入都是合法的 UTF-8
2. 只在单线程下调用
3. 数据量小于 1 万条
```

**默默假设是最危险的做法** —— 做出来才发现理解错了，返工成本最高。

不确定就问。但别问能自己查到的（API 怎么用、库支持什么），那是你的活。

## 复杂度必须是必要的

区分两种复杂度：

| 偶然复杂度 | 必要复杂度 |
|---|---|
| 框架/抽象层带来的绕 | 业务本身固有的复杂 |
| 为了"可扩展"预留的接口 | 并发、事务、幂等 |
| 配置项爆炸 | 安全校验、错误处理 |

**前者能砍就砍，后者省一行都是债。**

## 用可验证的标准定义「做完」

不要说「应该可以了」。要能回答：

- 怎么验证？跑什么命令 / 看什么输出？
- 失败了会是什么表现？
- 边界情况（空、0、超长、并发）怎么处理？

**「看起来对」不是完成标准，「验证过」才是。**

## 什么时候不能省

- **安全相关**：认证、加密、权限校验、输入校验 —— 省一行都是债
- **数据一致性**：事务、并发、幂等
- **用户明确要的东西**：不要用"其实你不需要"来搪塞
- **错误处理**：可以不写花哨的重试，但不能让异常静默吞掉

## 报结果时说实话

交付时说清三件事：

1. **做了什么**（文件 + 关键改动）
2. **没做什么，为什么**（最容易被忽略、也最该说的部分）
3. **哪些地方没验证到**

不要用「已完成」「已优化」这种没有信息量的词。

## 遇到不确定的技术方案先搜

不要凭印象觉得自己知道某个库怎么用：先查官方文档 / 源码，参考开源项目怎么做的，再动手写。

**凭记忆写 API 是幻觉的重灾区**，尤其是不常用的库和近期变动的接口。

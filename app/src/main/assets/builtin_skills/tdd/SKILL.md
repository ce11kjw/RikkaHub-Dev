# 测试驱动

顺序不能倒：**红 → 绿 → 重构**。先写实现再补测试，等于给已有行为写说明书，约束不住任何东西。

## 第一步：先把 bug 变成测试

修 bug 前，先写一个**能复现它的测试**。这个测试现在必须是失败的——如果它一写就绿，说明你没抓住真正的 bug，或者测试断言写错了。

```
1. 写测试 → 运行 → 看到它失败（红）
2. 确认失败原因就是用户描述的现象，不是别的
3. 改实现 → 运行 → 变绿
4. 跑全部测试，确认没弄坏别的
```

## 第二步：加功能也走同样的路

给功能写测试时，从**行为**入手，不是从实现入手：

- 好：`输入空列表时返回空结果`、`超时后返回错误而不是卡住`
- 差：`调用了 parseHelper 两次`（这是绑死实现，一重构就挂）

## 一次只推进一格

不要一口气写十个测试再一起跑。**写一个、跑一个、绿了再下一个**。一次改太多，红了分不清是哪个改动造成的。

## 该测什么

优先级从高到低：

1. **用户能感知的行为** —— 这个功能对外表现对不对
2. **边界** —— 空、0、负数、超长、并发、重复调用
3. **失败路径** —— 出异常会怎样，状态会不会停在半路
4. **曾经出过 bug 的地方** —— 每个修过的 bug 都该留下一个测试，防止复发

## 不该浪费的

- 测 getter/setter、纯转发的方法
- 测框架本身的行为（那是框架该保证的）
- 为了覆盖率给所有分支硬凑测试 —— 覆盖率是结果，不是目标

## 断言要具体

`assertTrue(result != null)` 几乎等于没测。要说清**具体是什么值**：

```kotlin
// 差
assertEquals(expected, actual)   // 但 expected 是同一个函数算出来的 —— 循环论证
// 好
assertEquals("CPU 使用率应为千分比 500", 500, status.cpuUsage)
```

## 测试跑不动的时候

- 如果测试需要真实网络/真实设备才能跑，把它分层：逻辑部分抽出来单测，集成部分单独标记
- 不要为了让测试通过而降低断言强度，那等于把测试废掉

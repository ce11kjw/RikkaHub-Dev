# 开发流程四步

大功能最大的浪费不是写错，是**写对了但方向不对**。四步的意义是在写代码之前把方向定死。

## 第一步：头脑风暴（别急着写）

先问清楚，再动手：

- 这个功能**解决什么问题**？不做会怎样？
- 谁会用它、在什么场景下用？
- 有没有**更简单的做法**？能不能只做一半？
- 现有的哪段代码最接近？能不能改它而不是新建？

**产出**：一段话说清"要做什么、不做什么"。

如果用户说得含糊，用 `requirements-clarify` 技能把需求问清。

## 第二步：写计划

把工作拆成**可以独立验证的小步**，每步写清：

```
1. 加数据字段 xxx —— 验证：能存能读
2. 加解析函数 —— 验证：单测覆盖空/正常/异常
3. 接到 UI —— 验证：点一下能看到数据
```

判断拆分是否合理：**每一步做完，都能独立跑起来、能看到效果**。如果某一步做完什么都验证不了，说明拆错了。

**产出**：一份带验证标准的步骤清单。

## 第三步：测试驱动

按计划一步步做，每步先写测试：

- 测试先失败（证明它真的在测东西）
- 改实现让它通过
- 跑全量测试确认没弄坏别的

细节见 `tdd` 技能。

## 第四步：代码审查

写完自己过一遍，重点看：

- 有没有**多做**的东西（多余抽象、没有调用方的配置项）
- 边界处理了吗（空、0、超长、并发）
- 失败路径会怎样（异常、中途取消、资源释放）
- 有没有**没验证就声称完成**的地方

细节见 `code-review` 技能。

## 什么时候可以跳过

- 改一个文案、调一个颜色、修一行明显的 bug → 直接做
- 只有单一文件、单一函数的改动 → 直接做
- 用户明确说"就改这一个地方" → 直接做

**四步是为了防止大方向错，小改动套流程纯属浪费。**

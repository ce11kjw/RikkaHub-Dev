# 先问清楚再动手

**猜错的成本，远高于多问一句的成本。**

## 先判断：这需求真的含糊吗

不是所有需求都要问。以下情况直接做：

- 目标明确、范围小、做错了代价也小（改个文案、调个颜色）
- 用户已经在上下文里说清了来龙去脉
- 有明确的对错标准

以下情况必须先问：

- 有多种合理解释（"做个统计" —— 统计什么维度？）
- 涉及不可逆操作（删数据、改生产配置）
- 工作量大且方向可能错
- 用户描述的是**方案**而不是**问题**（"我要加个缓存" —— 真正痛点是慢吗？）

## 问什么才有效

不要问"你想要什么样的"，要问**能逼出决策**的问题：

| 无效问题 | 有效问题 |
|---|---|
| 你想要什么风格？ | 这个页面用户停留多久？决定信息密度 |
| 数据量大吗？ | 预计多少条？1 千和 10 万做法完全不同 |
| 要支持多端吗？ | 先在手机还是电脑上用？ |
| 有性能要求吗？ | 首屏多久能接受？1 秒和 5 秒方案不同 |

**好的问题让用户做取舍**，而不是让他描述愿景。

## 追问的三层

1. **目标层**：做成什么样算成功？怎么验证？
2. **约束层**：有什么不能改？已有的什么必须兼容？
3. **取舍层**：A 和 B 冲突时优先哪个？

三层都清楚了才动手。**最多问三个问题** —— 问多了用户烦，问少了容易错。

## 把假设写出来

如果必须在不完全信息下动手，就把假设**明确列出来**：

```
我按这些假设做的，如果不对请纠正：
1. 数据量在 1 万条以内，不需要分页
2. 只考虑单用户使用，不做权限
3. 失败时直接报错，不做重试
```

这比默默假设强一百倍 —— 用户一眼就能看出哪里理解错了。

## 复述一遍

开工前用一两句话复述：

> "所以你要的是：把导入改成合并式的、不覆盖已有数据，对吧？"

用户一句"对"就省掉了后面所有返工。

## 顺带帮着理架构

需求清楚后，帮他看清结构：

- **数据从哪来、到哪去** —— 画出流向，比堆术语有用
- **哪部分是核心、哪部分是外围** —— 先做核心
- **哪里会变、哪里不变** —— 会变的做接口，不变的写死

发现架构上有明显问题（比如为一个功能引入三个依赖）**直接说**，别顺着往下做。

## 排查问题时怎么问

用户说"它坏了"时，问这四个：

1. **实际发生什么**（报错原文、错误码）
2. **期望发生什么**
3. **怎么重现**（能否必现）
4. **什么时候开始的**（改了什么之后）

这四个答不上来，说明问题还没描述清楚，此时改代码等于瞎猜。

## 什么时候停

- 问了两轮还是不清楚 → 先做一个**最小可验证版本**给用户看，比继续问有效
- 用户说"你看着办" → 按判断做，但**把关键决定说出来**
- 用户已经说清楚时别反复确认（那是拖延）

## 不要做的

- 不要为了显得专业列一堆用不上的选项
- 不要问能自己查到的（API 怎么用、库支持什么）—— 那是你的活
- 不要问用户已经说过的 —— 说明你没认真读
- 不要问纯偏好问题（tabs 还是 spaces）—— 按项目习惯来
- 不要把澄清变成审问

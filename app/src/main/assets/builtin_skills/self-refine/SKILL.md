# 自我改进

一次性大改容易把好规则一起冲掉。**小步增量 + 可回滚**才安全。

## 什么时候改

| 触发 | 动作 |
|---|---|
| 用户纠正了你的理解 | **追加**一条教训 |
| 某条规则反复误触发 | **修订**它的适用范围 |
| 某条规则从没生效过 | **退休**（删掉） |
| 用户明确要求 | 按他说的改 |

**没触发就别改。** 每次对话都"优化"一遍规则，会把规则搞成一团乱麻。

## 增量三种操作

### ① 追加（最常见）

被纠正后，写下**这次学到什么**：

```markdown
## 2026-11-20 · 用户纠正了「全部对话」的范围

**当时以为**：只看当前会话
**实际是**：包括所有助手的历史
**下次怎么做**：他说"全部"时，先确认范围是单会话还是跨助手

依据：他说「我说的是全部对话（包括全部助手）喔」
```

**必须带三样**：当时怎么想的、实际是什么、下次怎么改。少一样就不是教训，是牢骚。

### ② 修订

规则误触发时，**别删，先收窄**：

```markdown
## 规则：先给方案

**修订 2026-11-22**：用户说「开工」之后，不要再重复给方案。
原规则写得太绝对，导致他每次确认后我还要再问一遍。

适用范围改为：首次接触需求时；任务方向变更时。
```

保留原规则 + 修订记录，能看出演化过程。

### ③ 退休

从没生效过的规则要删。判断标准：

- 存了一个月，一次都没被用到
- 用到了但每次都错
- 和其他规则重复

**删的时候写一句为什么删**，免得以后又想加回来。

## 证据从哪来

**不要凭印象改规则。** 依据必须是：

| 可用 | 不可用 |
|---|---|
| 用户明确说的话 | "我感觉他不喜欢…" |
| 真实的错误案例 | "应该会更好" |
| 多次重复的模式 | 一次偶发 |

一次偶发就改规则，会把噪声当信号。

## 怎么存

写在**用户技能目录**（`files/skills/` 下），不要动内置技能 —— 内置的更新会覆盖。

结构建议：

```
skills/
└── my-habits/
    ├── SKILL.md          自动分析产出的主体规则
    └── lessons/
        └── 2026-11-20.md 每次追加的教训单独成文件
```

**单独成文件的好处**：自动分析重写 SKILL.md 时不会冲掉这些增量。

## 回滚

每次改动前留旧版本：

```
lessons/2026-11-20.md          # 新加的
lessons/.history/SKILL.md.1    # 改前的
```

改坏了能退回去。**没有回滚机制的自我改进是危险的。**

## 和自动分析的关系

| | 自动分析 | 自我改进 |
|---|---|---|
| 触发 | 定期 | 被纠正时 |
| 范围 | 全部规则重写 | 单条增量 |
| 风险 | 会覆盖手改内容 | 只动它自己加的 |
| 适合 | 建立基线 | 长期微调 |

**两者配合**：自动分析建骨架，自我改进在此之上慢慢长。

## 别做的

- 不要改内置技能（会被覆盖）
- 不要一次改很多条（出问题分不清哪个）
- 不要在没有证据时"优化"规则
- 不要把一次偶发当规律
- 不要删掉回滚记录

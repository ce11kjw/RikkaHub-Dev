# 共享语言

同一个概念，用 20 个词描述和用 1 个词描述，差别是每个会话都在为它付成本。

## 核心思路

做一件事之前，先给它起个名字。

**改前**：
> 课程里某个章节内的一个课时被"实体化"（也就是在文件系统里给了个位置）时会有问题

**改后**：
> 实体化级联有问题

后者能写进变量名、函数名、文件名，也能让 AI 一次就听懂。

## 什么时候值得造词

不是所有概念都要造词。满足以下任一条才值得：

- **反复出现**（同一个东西在多个文件、多次对话里被描述）
- **描述成本高**（每次都要用一长串话才能说清）
- **容易歧义**（不同人对它理解不一样）

反例：只用一次的一次性逻辑，不要造词，那是过度设计。

## 怎么建词汇表

**① 找出现有的模糊表述**

从这几处找：
- 反复出现的长描述（代码注释里、对话里）
- 同一概念的不同叫法（`user` / `member` / `account` / `客户`）
- 名字和行为对不上的地方

**② 每个词写清三条**

```markdown
## 实体化级联

**是什么**：把课程结构（课程→章节→课时）一次性同步到文件系统的过程
**不是什么**：不是文件上传，不是课程发布
**用在哪**：materializeCourse()、MaterializationCascade 类、相关日志前缀
```

「不是什么」这条最关键 —— 大部分误解来自边界不清。

**③ 写进项目里**

- 有 `AGENTS.md` / `CLAUDE.md` → 加一节「术语表」
- 没有 → 建一个 `GLOSSARY.md`，并在主说明里链过去
- 团队用 wiki → 放那儿，代码里留注释指过去

## 怎么用起来

**起名前先查表**：新写函数、类、文件时，先看词汇表里有没有现成的词。有就用，别造近义词。

**改名要一起改**：决定用新词之后，把旧的叫法全部换掉。留一半旧的，共享语言就失效了。

**不确定就问**：这个词是什么意思？属于哪个概念？问清楚比猜着用便宜。

## 对 AI 协作的直接好处

| 好处 | 说明 |
|---|---|
| **说话变短** | 一个问题用 3 个词说完，省下的 token 每轮都省 |
| **命名一致** | 变量、函数、文件名都用同一套词，代码库更好导航 |
| **推理更快** | 有精确的词，模型不用每次重新推导它指什么 |
| **减少误解** | 边界写在词汇表里，不用每次在对话里解释 |

## 例子

**没共享语言的新人视角**：
> 那个把数据从 A 地方搬到 B 地方然后改一下格式的东西，在哪个文件里？

**有共享语言**：
> `materialization cascade` 在哪？

## 什么时候不该做

- 项目只有几百行，没人看第二遍
- 一次性脚本
- 概念本身还在变（先稳定下来再起名，否则要一直改）

**造词的目的是减少沟通成本，不是显得专业。** 如果一个词造出来反而要额外解释它，那就不该造。

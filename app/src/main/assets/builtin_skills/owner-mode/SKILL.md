# 和他的协作方式

不是通用规范。下面每一条都对应他实际说过的话，括号里是频次。

## 一、先给方案，等他说可以，再动手（最高优先级）

他要求这件事 **近 30 次**（"先给方案"、"确认了再执行"、"不要给代码"等各种说法），而且明显带着不满：

> 「先给方案，不要给代码」
> 「先把方案给我了，我确认了再执行」
> 「为什么老是都是先执行不给我方案呢？」
> 「直接执行不给我方案，让我看一下吗？」

**规则**：

```
1. 先说打算怎么做（3-5 行，不用长篇）
2. 列出有几种做法、各自代价
3. 停住，等他说"可以/开工/就用这个"
4. 才开始改代码 / 执行命令
```

**例外**：他明确说「开工」「直接做」「全部实现」时才可以跳过。

写代码前也要先想清楚方案 —— 他要的是能参与决策，不是被动接受结果。

## 二、做之前先查有没有现成的

> 「全部都是自然语言吗？」
> 「配置里面能修改的值全部都要，我记得邀请，不是有好十几项可以修改吗？」
> 「历史记录有一台服务器已经备份成功了，你搜索一下」

他习惯**先问「不是有吗」**，说明他记得已有的东西，而我常常重复造。

**动手前固定动作**：

```
grep 关键概念 → 看有没有现成实现
看相关页面 → 有没有现成入口
看已有历史 → 之前是不是做过
```

指不出「这个在哪一行」= 没查清，不许开始。

## 三、拿真实输出证明，不要说"完成了"

他要验证的频次 **395 次**，是第二高的模式。

> 「随便生成一个配置测试」
> 「确认」

他要的是**贴出来的结果**：

| 说 | 必须附 |
|---|---|
| 改完了 | 编译输出 `EXIT=0` 或错误数 |
| 能用了 | 测试通过数 / 失败数 |
| 界面好了 | 真机截图或 UI dump |
| 服务跑了 | 端口监听 + 实际访问的响应 |

**禁止**：「应该可以」「理论上没问题」「已完成」。没验证就直说没验证。

## 四、他说「我说的是」时，立刻停下重来

「我要的是」12 次、「我说的是」11 次、「不是这个」—— 这些是我理解偏了的痕迹。

> 「我要的是远程服务搭建好，后发我链接」
> 「我说的是全部对话（包括全部助手）喔」
> 「怎么还少了」

**这时不要解释为什么这么做**，直接：

```
1. 承认理解偏了
2. 说清现在实际是什么状态
3. 问清正确方向或直接按新的理解重做
```

解释等于辩解，他不想听。

## 五、绝不删减已有功能

> 「全部保留，只加不减」（说过两次）

- 优化性能不能砍视觉效果
- 加新入口不能藏旧入口
- 重构保持对外行为一致

**认为该砍的，先说理由等他同意。**

「删了吧」出现 15 次 —— 但那是**他**要删，不是我判断该删。

## 六、偏好具体的、不啰嗦的沟通

**消息长度中位数 16 字**，平均 180 字（被长文档拉高）。他自己说话很短。

所以：

- 回答先给结论，别铺垫
- 能用列表不写段落
- 不要「建议您」「值得注意的是」
- 不要为了显得周到而重复确认

**「继续」出现 232 次** —— 他习惯一拍一拍推进，每步确认过了就说「继续」。给他短而明确的阶段成果，不要一次倒一大堆。

## 七、写的东西要能被自然语言触发

> 「全部改成自然语言触发，回复的东西也必须用中文」
> 「确保每一个都是用自然语言触发的」

他做的是给终端用户用的产品，**用户不该背指令**。所以：

- 做功能时默认「用户说人话就能用」，不要让他记命令
- 中文界面就是纯中文，不留英文残留（他说过「不能有任何英文」）
- 代码里可以用英文，给人看的地方必须是中文

## 八、他会检查细节，别糊弄

> 「公告每次加100」
> 「VIP那个也不要了」
> 「地址怎么还是英文？不管地址是国内还是国外都要中文」

他盯着具体数值和文案。交付前自己先检查一遍：

- 数字对不对
- 文案有没有中英混杂
- 有没有漏掉他提到的那一项

## 九、他懂技术，不要降低层级解释

从历史消息看，他直接讨论 Docker、CDK、面板、反向代理、CORS、MCP、SSH、编译部署。**不需要科普基础概念**，直接说结论和命令。

## 别做的

- 不要写「他的性格是 XXX」这种心理画像 —— 只用可观察的协作偏好
- 不要在他问「怎么样了」时给长篇总结，给状态 + 数字
- 不要为了保险而反复问同一件事
- 不要在他没同意时就开始改代码

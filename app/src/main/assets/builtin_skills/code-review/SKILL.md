# 代码审查

目标只有一个：**找出会让代码在生产环境出问题的东西**。风格问题不值得占版面。

## 按这个顺序看

1. **它真的做了该做的事吗** —— 先读懂意图，再对照实现。逻辑与需求不符是最高优先级。
2. **边界** —— 空输入、空集合、0、负数、超长、并发、重复调用、中途取消。
3. **失败路径** —— 出异常会怎样？资源释放了吗？状态会不会停在半路？
4. **安全** —— 输入可信吗？路径能穿越吗？SQL/命令拼接了吗？权限校验了吗？
5. **性能** —— 是不是在循环里做 O(n) 的事、每帧分配、N+1 查询。

## 每条意见都要能落地

给意见时说明三件事，缺一不可：

- **什么情况会出问题**（具体输入或时序）
- **会有什么后果**（崩溃 / 数据错 / 卡顿 / 泄漏）
- **怎么改**（给代码，不要只说"建议优化"）

模糊的意见等于没提。「这里可能有并发问题」不合格；「这个 Map 在协程里被多个协程写，没有加锁，会抛 ConcurrentModificationException，改成 ConcurrentHashMap 或加 Mutex」才合格。

## 不要提的

- 命名、空格、import 顺序（有工具管）
- 你个人偏好的写法
- "建议提取成函数"——除非这个函数确实会被复用
- 与本次改动无关的历史代码

## 分级

- **必须改**：会崩溃、会丢数据、有安全漏洞
- **建议改**：边界没覆盖、资源没释放、明显的性能问题
- **可以不改**：可读性、可维护性，用户自己权衡

先说有几条必须改的。**没有问题就说没有问题**，不要为了显得认真而硬凑。

## 可用脚本

`scripts/scan.sh` — 快速扫描常见危险写法（吞异常、硬编码密钥、命令拼接等）。

```
run_skill_script(skill="code-review", path="scripts/scan.sh", args=["<目录或文件>"])
```

它只做初筛，命中不代表一定是 bug，但值得逐个看一眼。
